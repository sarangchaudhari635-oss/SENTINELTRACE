# SentinelTrace
### Real-Time Security Event Monitoring and Rule-Based Threat Detection

SentinelTrace is a Java web application that ingests security events, applies deterministic detection rules, creates evidence-backed incidents, and presents them through a dashboard. It is designed as a one-day college mini-project MVP.

> **Important scope note:** SentinelTrace is a learning/demo application. It uses generated events and configurable rules. An alert indicates that a rule matched, not proof that a real attack occurred.

## Problem Statement
Reviewing authentication and application logs manually can make repeated failed logins and unusual request bursts difficult to spot. SentinelTrace demonstrates how events can be normalized, stored, evaluated against transparent rules, and surfaced as incidents.

## Objectives
- Ingest and persist security events.
- Detect repeated failed logins and high-volume HTTP requests using time-window rules.
- Create and update incidents without producing a new incident for every matching event.
- Show event history, incidents, severity, and status in a web dashboard.
- Record incident status changes in an audit trail.
- Demonstrate Java, Spring Boot, REST APIs, relational databases, validation, and automated tests.

## MVP Features
1. Dashboard summary and recent incidents.
2. Event list with basic filters.
3. Event ingestion REST endpoint.
4. Demo event generator.
5. Failed-login threshold rule.
6. HTTP request burst rule, if time permits after the first rule works.
7. Incident detail, acknowledge, and resolve actions.
8. PostgreSQL persistence.
9. Input validation and centralized error handling.
10. Tests for detection thresholds and API validation.

## Architecture
Browser (Thymeleaf/Bootstrap/Chart.js) → MVC/REST Controllers → Services (ingestion, detection, incidents, analytics) → Spring Data JPA Repositories → PostgreSQL.

The event flow is:
1. Validate request.
2. Persist event.
3. Evaluate enabled detection rules.
4. Create or update a matching active incident.
5. Record incident lifecycle changes.
6. Render updated metrics and incident lists.

## Quick Start
### Prerequisites
- JDK 21
- Maven (or use the Maven Wrapper generated by Spring Initializr)
- PostgreSQL
- IntelliJ IDEA or VS Code with Java support

### Create the database
```sql
CREATE DATABASE sentineltrace;
```

### Configure environment variables
Set `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD`. Example local URL:
`jdbc:postgresql://localhost:5432/sentineltrace`

### Configure `src/main/resources/application.properties`
```properties
spring.application.name=sentineltrace
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/sentineltrace}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD}
spring.jpa.hibernate.ddl-auto=update
spring.jpa.open-in-view=false
server.port=8080
```
`ddl-auto=update` is acceptable for a quick local demo. For a more controlled version, add Flyway migrations and set `ddl-auto=validate`. Never commit credentials.

### Run
```bash
./mvnw spring-boot:run
```
On Windows:
```powershell
.\mvnw.cmd spring-boot:run
```
Or use `mvn spring-boot:run` if Maven is installed.

Open `http://localhost:8080`.

### Test and package
```bash
./mvnw test
./mvnw clean package
```

## Detection Rules
### Failed login rule
Trigger when at least 5 `LOGIN_FAILURE` events from the same source IP occur within a rolling 5-minute window. The threshold is a demo configuration, not a universal security standard.

### HTTP request burst rule
Optional second rule: trigger when at least 30 `HTTP_REQUEST` events from one source IP occur within a rolling 60-second window.

Use event timestamps consistently, validate acceptable timestamp ranges, and explain the matched rule and evidence count in the incident.

## Data Model
- `security_events`: normalized source events.
- `detection_rules`: configurable thresholds and severity.
- `incidents`: grouped detections and status.
- `incident_audit_logs`: lifecycle history.

See `docs/DATABASE_SCHEMA.md` and `database/schema.sql`.

## Testing
- Below threshold does not create an incident.
- At threshold creates an incident.
- Events outside the time window are excluded.
- Different IP addresses are counted separately.
- Matching events update an active incident instead of creating duplicates.
- Invalid payloads return HTTP 400.
- Status changes produce audit records.
- Data persists after application restart.

## Security and Limitations
- Use synthetic/demo events; do not scan or attack real systems.
- Protect management routes before exposing the app beyond localhost.
- Validate input and avoid logging credentials, tokens, or unnecessary personal data.
- Keep secrets in environment variables.
- Rule-based detections can produce false positives and do not prove compromise.
- A one-day MVP is not a production SIEM and does not include high availability, distributed processing, or guaranteed delivery.
